# Weather service reliability

Task 4 runs on `fix/weather-service-reliability`, based on `origin/main` at `0b0886e`, including merged geolocation work. The user authorized implementation, atomic commits, and branch delivery, and will create the PR.

## Decisions

- `weather.service.ts` is a server-only module rather than a Server Action module. Its existing async `getWeather` and `getForecast` entry points remain available to server callers. The weather server component also uses the server-only boundary.
- `weather/request.server.ts` validates coordinate strings and the runtime API-key binding before starting a request. Coordinates remain the selected database record's exact values; units remain metric and language remains English. Missing configuration and invalid coordinates fail before contacting the provider.
- Each provider request has one 10-second deadline covering both headers and body. The deadline aborts the request and rejects even if an underlying operation ignores its abort signal. Timers are cleared, unsuccessful or late response bodies are discarded, and late completions cannot replace the failure result.
- `WeatherServiceError` exposes a code for missing configuration, invalid coordinates, network failure, timeout, HTTP failure, or invalid data. HTTP failures preserve their status, allowing callers to distinguish 401/403, 404, 429, and 5xx. Messages are fixed strings. Provider bodies, request URLs, raw transport errors, and their potentially sensitive causes are not attached or logged by the service.
- `weather/payload.server.ts` treats decoded JSON as unknown. It checks object/array structure, required strings and finite numbers, humidity/cloud ranges, wind speed/direction, coordinates, and provider error envelopes before mapping domain objects. No new validation dependency is needed.
- Missing wind direction and solar times become `null`, reflected in the `Weather` type. Missing country metadata becomes an empty string. Missing or unrecognized icon codes map to `unknown`; malformed icon field types fail validation. Valid zero values are preserved.
- Forecast parsing checks every entry, including entries that will not be selected, validates UTC calendar timestamps, and preserves the existing noon-UTC sample behavior and provider order. Empty lists are accepted. The forecast service remains available for later features.
- The 600-second cache is moved from raw fetch responses to validated domain objects using Next.js `unstable_cache`. Its keys use endpoint namespaces and coordinate arguments, without passing credentials as cache arguments. Provider fetches use `no-store`, so malformed HTTP 200 payloads and failures cannot enter the weather-data cache. The versioned namespaces should change when the cached domain shape changes. Next's stale-while-revalidate behavior may serve previous valid data while a refresh is attempted; this is not a hard maximum age.
- Matching in-flight provider requests share a promise within the current server process, keyed by endpoint and exact coordinates. The pending entry is removed on either success or failure. This prevents a preference-saving re-render from duplicating an initial cold-cache weather request. Different endpoints or coordinate pairs remain independent; separate server processes do not share this map.
- `WeatherCardServer` requests only current weather. The unused forecast request and its `console.log` are removed. Existing component markup and styles are preserved.

## Validation

Before implementation, two regression tests failed against the previous service: HTTP 503 became `City not found`, and a string temperature became a successful result containing `NaN`. Both pass with the new service.

- `npm test`: **261 tests passed across 14 files**, including the existing 146 and 115 new tests. Final cloud duration was 105.93 seconds, with 3.81 seconds executing tests; the large city JSON imports still dominate startup.
- The new tests cover successful weather/forecast mapping, numeric and structural validation, optional fields, valid zero values, icon mapping, UTC timestamp validation, exact request coordinates, runtime configuration, 400/401/403/404/429/500/503, malformed JSON, body disconnection, stalled headers, stalled bodies, abort-ignoring operations, late results, timer cleanup, safe errors, concurrent-request sharing, retry after a shared failure, and the removed forecast/log side effects.
- `npm run lint`: passed.
- `npm run build`: passed, including TypeScript, on Next.js 16.4.2 with the lead's 4 GB Node heap setting.
- Unit tests bypass the Next cache wrapper; a separate production integration check exercises the actual framework cache. A temporary provider adapter outside the checkout simulated 503, invalid temperatures, malformed JSON, stalled headers, stalled body, 401, 429, network failure, and an error envelope inside HTTP 200. Every failure was followed by a successful request at the same coordinates, then a cache hit without another provider request. Missing optional metadata and a zero temperature also rendered successfully. Two concurrent cold-cache page requests shared one provider call. All **11 scenarios passed**, with 20 provider requests and no forecast calls. Header/body hangs aborted after 10,015/10,017 ms in the final run.
- Fixture weather cache entries were removed before the live checks. A separate production process used the inherited proxy and TLS settings with the real configured OpenWeather credential. A pass-through observer recorded only endpoint paths and coordinates, without credential values or query strings.
- System Chromium **154.0.8037.57** passed **five live browser scenarios**: weather rendering for Moscow and both Suzhou records, search navigation with remembered-city persistence, and a 375 px mobile viewport. The actual weather provider was used, no JavaScript page errors occurred, and the final observer recorded exactly three current-weather requests for the three distinct coordinate pairs. The first browser run exposed two cold-cache calls per city during preference-saving re-renders; the in-flight sharing fix reduced six calls to three in the repeated run. The mobile screenshot was inspected for viewport fit.
- Production adapters, observers, browser runner, results, and screenshots live temporarily under `/tmp/weather-reliability-audit/`. No browser dependency or test endpoint was added to the app.

## Remaining work

Page-level recovery is task 5. Service failures still propagate to Next's existing error handling; this task does not add a weather error panel, a retry button, or preserve the search UI through an uncaught page failure. Production React Server Component errors redact custom details, so the next task must map service failures on the server rather than assume these error codes reach the browser boundary.

Provider schema changes can surface as `invalid_response` and should be handled explicitly. Live checks covered the current provider's responses for three selected locations, not every climate, account plan, or provider condition. The 10-minute cache's expiry/stale-refresh timing was inspected in the framework implementation; the production harness checked fresh hits and rejection of invalid results without waiting ten minutes.
